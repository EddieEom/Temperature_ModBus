## 장비 IP를 확인하기까지

**증상**  
spFinder에서 장비 IP·MAC을 확인하지 못했고, 추정 주소로 TCP 502 연결을 시도해도 실패했습니다.

**확인 과정**  
노트북 Wi-Fi, 장비 Ethernet, 학교 스위치의 배선 경로를 확인했습니다. 스위치의 물리 포트 번호 47을 IP 주소의 마지막 자리로 해석해 접속했던 것이 문제였습니다. 노트북 유선 어댑터에 보이는 169.254 대역 주소도 장비 주소와 구분할 필요가 있었습니다.

**조치와 결과**  
실제 배선을 따라 연결 경로를 확인하고 공유기의 DHCP 목록에서 장비 주소를 식별했습니다. 확인한 주소를 WinForms에 입력한 뒤 TCP 연결에 성공했고, 단건 Modbus 요청에서 25.0℃를 확인했습니다.

**기록할 확인 순서**

1. 장비 전원과 Ethernet 링크 확인
2. PC와 장비가 연결된 실제 네트워크 경로 확인
3. spFinder·DHCP 목록에서 장비 MAC과 IP 대조
4. TCP Server·Modbus Slave·502·Unit ID 설정 확인
5. 확인된 주소로 연결 후 실제 레지스터 응답 확인

해결의 핵심 근거는 실제 장비 주소를 찾아 입력한 뒤 연결된 결과입니다. DHCP 자동 할당 기능을 새로 구현해 해결한 것으로 기록하지 않았습니다. USB 가상 COM 미인식의 구체적인 원인은 당시 기록에서 확정되지 않았습니다.

## TCP 응답 경계와 온도 해석

**구현 과정에서 고려한 문제**  
TCP Read 한 번으로 Modbus 응답 전체가 도착한다고 가정하면 헤더나 데이터 일부만 읽을 수 있습니다. 온도 WORD를 부호 없는 값으로만 처리하면 음수 값을 잘못 해석할 수 있습니다.

**반영한 처리**  
헤더와 본문을 ReadExactlyAsync로 나눠 읽고, 요청·응답 Transaction ID, Protocol ID, Unit ID, Length, FC04 및 바이트 수를 확인했습니다. 온도는 unchecked((short)raw) / 10.0으로 변환했습니다.

정상값 250 → 25.0℃는 시험 기록에서 확인됩니다. 분할 패킷·음수·잘못된 헤더를 주입한 회귀시험 결과는 별도 확보가 필요합니다.

## 그래프 한글과 시간축

**문제**  
기본 글꼴에서 한글 축 이름과 시간 표기의 글자가 올바르게 표시되지 않는 문제를 다뤘습니다. 장비 측정 범위 전체를 Y축에 표시하면 실습 온도 변화가 작게 보이는 점도 조정했습니다.

**반영한 처리**  
NotoSansCJKkr-Regular.otf를 프로젝트에 포함하고 FileFontResolver로 등록했습니다. 시간축은 HH:mm:ss 형식으로 바꾸고, Y축은 현재 코드에서 20~100℃로 설정했습니다. 고온·복귀 기준선을 표시하고 관측 공백은 NaN으로 표현합니다.

**현재 확인 위치**  
MainForm의 RegisterChartFont, InitializeTemperatureGraph, AppendTemperaturePoint와 csproj의 폰트 복사 설정입니다.

## 알람 발생 온도가 계속 바뀌는지 확인

**검토한 문제**  
최신 온도와 최초 알람 발생 온도를 혼동하면 과거 알람의 발생 조건을 설명하기 어렵습니다.

**반영한 처리**  
SaveHighTemperatureAlarm은 활성 알람이 없을 때만 AlarmEvent를 INSERT합니다. 고온이 지속되는 동안 TriggerTemperature를 갱신하지 않고, 정상 복귀 시 같은 행의 RecoveredAt을 채웁니다. 같은 장비·종류의 미복귀 알람 중복은 필터링된 고유 인덱스로 제한합니다.

**확인 사례**  
알람 19번의 발생 온도 93.6℃를 기준으로 발생·확인·복귀 이력을 대조했습니다. 최초 발생 온도를 실시간 현재 온도와 별도 의미로 관리합니다.

## 확인 버튼과 정상 복귀 구분

**검토한 문제**  
작업자 확인과 장비 정상 복귀를 한 상태로 합치면 아직 고온인 알람을 종료하거나, 복귀한 미확인 알람을 놓칠 수 있습니다.

**반영한 처리**  
확인 버튼은 AcknowledgedAt만 기록합니다. 정상 복귀는 별도 판정 후 RecoveredAt에 기록합니다. 활성 화면은 미복귀 또는 미확인 건을 표시합니다.

**기록된 결과**  
알람 19번의 16:07:35 발생, 16:08:00 확인, 16:08:19 복귀를 각각 확인한 시험 기록이 있습니다.

## 센서 오류·수신 공백과 연속 판정

**검토한 문제**  
수신 실패 전후의 샘플을 이어 세거나 마지막 온도를 현재값으로 계속 표시하면 실제 관측과 다른 상태를 보여줄 수 있습니다.

**반영한 처리**  
센서 오류는 상태 레지스터로 구분하고, 통신 오류는 수신 예외·시간 초과로 구분합니다. 오류 시 현재 온도를 대시로 바꾸고 그래프 선을 끊으며 연속 고온·복귀 카운트를 초기화합니다. 기존 고온 상태는 유지하고 정상 온도 수신 후 복귀 조건을 다시 판정합니다.

이 처리는 현재 소스에서 확인한 사항입니다. 센서선 제거·LAN 제거의 실제 반복시험 결과는 [시험 문서](verification.md)에 후속 항목으로 남겼습니다.

## 복귀 후 DB 상태 문구

**증상**  
정상 복귀 저장 후에도 DB 상태가 알람 저장 완료로 남는 표시 문제를 다뤘습니다.

**반영한 처리**  
SaveAlarmStateAsync에서 발생 저장이면 알람 발생 저장, 복귀 저장이면 DB 정상으로 표시합니다. 현재 코드는 각각 DB: 알람 발생 저장, DB: 정상 문자열을 사용합니다.

DB 접속 실패와 알람 저장 실패, 카카오 처리 오류가 같은 상태 라벨을 공유하므로 마지막으로 처리한 작업의 문구가 표시될 수 있습니다.

## 카카오 발송과 상태 추적

**기록된 오류**  
카카오 연동 과정에서 403/-402와 talk_message 권한 부족을 확인한 뒤, 권한·토큰을 점검해 200 OK 및 시험 메시지를 확인했습니다.

**현재 처리**  
토큰은 사용자 비밀 Kakao:AccessToken에서 읽습니다. HTTP 성공과 result_code 0을 확인한 뒤 SENT를 기록하고, 오류 내용은 LastError에 남깁니다. 빈 토큰이면 화면에 설정 필요 상태를 표시합니다.

**발송 대기 확인 순서**

| 상태 | 확인할 항목 |
| --- | --- |
| 토큰 없음 | 사용자 비밀 키와 실행 프로젝트 일치 여부 |
| PENDING·AttemptCount 0 | currentDeviceId, 미복귀 HIGH_TEMP 여부, 작업 실행 여부 |
| PENDING·AttemptCount 1 이상 | 선점 후 중단·결과 저장 실패 여부 |
| FAILED | LastError, HTTP 응답, 토큰·권한 |
| SENT | API 성공 기록과 실제 메시지 대조 |

현재 자동 발송 대상은 AttemptCount 0인 건입니다. 실패 건 자동 재시도나 중단된 선점 건 회수는 구현되어 있지 않습니다. 발송 요청 직후 응답이 유실되면 실제 메시지가 도착했는지는 별도로 대조해야 합니다.

## 이력 날짜와 DB 시간

**확인한 처리**  
DB는 UTC를 사용하고 이력 화면은 한국 시간 날짜 범위를 UTC로 변환합니다. 종료일 다음 날 0시 미만 조건을 사용해 종료일 전체를 포함합니다. 시작일이 종료일보다 늦으면 조회를 막고, 조회 중복 실행과 닫힌 폼 갱신을 제한합니다.

대화에서 이력 조회 예외를 다룬 기록은 확인되지만, 정확한 최초 예외 메시지와 단일 원인을 현재 자료만으로 확정하기 어려워 특정 오류명을 붙이지 않았습니다.

## 새 PC의 DB 설정

현재 MainForm의 정적 DB 연결 문자열은 사용자 비밀 값이 없으면 InvalidOperationException을 발생시킵니다. 따라서 Git에서 소스를 받은 뒤 사용자 비밀 설정이 필요합니다. SQL 로그인 생성만으로 DB 테이블·프로시저 실행 권한까지 생기지는 않으므로 접속 계정의 DB 권한도 맞춰야 합니다.

장비는 DB의 LastKnownIp와 TcpPort로 조회합니다. DHCP 변경 뒤 주소가 바뀌면 실제 주소를 확인하고 DB 정보를 수정해야 합니다. 시작 시 입력 자동 채움에는 특정 MAC을 조회하는 코드가 있어 다른 장비 사용 시 해당 부분을 검토해야 합니다.

## 로컬 Git 연결과 최초 업로드

**발생한 오류**

| 오류 | 당시 상태와 처리 |
| --- | --- |
| destination path already exists | 기존 프로젝트 안에서 같은 이름으로 clone을 시도함 |
| not a git repository | 기존 폴더에서 git init으로 저장소 시작 |
| origin/main unknown revision | 원격 브랜치가 로컬에 확보되지 않은 상태에서 reset 시도 |
| .vs의 vsidx Permission denied | Visual Studio 임시 파일이 추가 대상에 포함됨 |

최종적으로 .gitignore에 .vs/, bin/, obj/, *.user, secrets.json을 추가하고 로컬 파일을 커밋했습니다. 실행 로그에서 67개 파일 등록과 main → main 업로드, origin/main 추적 설정 완료를 확인했습니다.

다음 작업부터는 같은 로컬 폴더에서 변경을 커밋해 push하고, GitHub에서 문서를 수정한 뒤에는 로컬 변경 상태를 확인해 pull로 동기화합니다.
